# Раздел 3. Доработка модели прогнозирования успеваемости до MLOps-конвейера

## 3.1 Исходное состояние модели

В качестве исходной версии использовался исследовательский notebook `model_2025_final_v3.ipynb`. В нем была реализована базовая логика машинного обучения:

- загрузка данных из файла `marks_25_hash.csv`;
- преобразование результатов ЕГЭ в отдельные признаки `EGE_*`;
- нормализация обозначений учебных семестров;
- перевод итоговых оценок в числовую шкалу;
- расчет среднего балла студента по каждому семестру;
- формирование исторических признаков `history_mean` и `last_mark`;
- обучение модели LightGBM с подбором параметров через Optuna;
- оценка качества модели на отложенной выборке.

Таким образом, исходный notebook решал исследовательскую задачу построения модели, однако не был готов к промышленному использованию. Основные ограничения notebook-подхода заключались в отсутствии модульной структуры, автоматизированного запуска, сохранения версий моделей, API для инференса и мониторинга предсказаний.

## 3.2 Цель доработки

Целью доработки являлось не создание новой модели с нуля, а перенос существующей логики из notebook в воспроизводимый MLOps-конвейер. При этом была сохранена ключевая идея исходной модели: прогнозирование будущего среднего балла студента на основе предыдущей академической истории, результатов ЕГЭ и характеристик образовательного подразделения.

## 3.3 Перенос логики notebook в модульную архитектуру

Исходный код notebook был разделен на несколько независимых модулей:

- `src/features.py` — перенос логики формирования признаков из notebook;
- `src/train.py` — обучение модели и сохранение артефактов;
- `src/predict.py` — загрузка модели и выполнение предсказаний;
- `api/app.py` — REST API для получения прогнозов;
- `src/logger.py` — логирование действий системы;
- `src/monitor.py` — логирование предсказаний и подготовка к мониторингу качества.

Особое внимание было уделено модулю `src/features.py`. В него перенесены функции нормализации семестров, построения GPA-таблицы и формирования обучающего набора. В исходном notebook один студент мог использоваться для нескольких обучающих примеров: например, первые два семестра применялись для прогнозирования третьего, первые три — для прогнозирования четвертого и т.д. Эта логика была сохранена в методе `build_notebook_training_dataset`.

## 3.4 Формирование признаков

В доработанном конвейере используются следующие группы признаков:

- результаты ЕГЭ, развернутые в отдельные признаки `EGE_*`;
- признак `history_mean`, отражающий средний балл студента за известные предыдущие семестры;
- признак `last_mark`, отражающий последний известный средний балл;
- `Курс_по_порядку`;
- категориальный признак `Подразделение`.

Целевая переменная `target` соответствует среднему баллу студента в следующем семестре. Такой подход уменьшает риск утечки данных, так как для прогноза используются только предыдущие семестры, а не информация из будущего периода.

## 3.5 Обучение и сохранение модели

Вместо ручного запуска ячеек notebook был реализован единый training pipeline:

```bash
python -m src.train
```

При запуске выполняются следующие этапы:

1. Загрузка исходного CSV-файла.
2. Формирование признаков по логике исходного notebook.
3. Разделение данных на обучающую и тестовую выборки.
4. Кодирование категориальных признаков.
5. Обучение модели LightGBM.
6. Расчет метрик качества `RMSE`, `MAE`, `R2`.
7. Сохранение модели в `models/model_v1.pkl`.
8. Сохранение метаданных модели в JSON-файл.

Таким образом, процесс обучения стал воспроизводимым и не зависит от ручного выполнения отдельных ячеек.

## 3.6 Инференс и API

Для использования модели вне notebook был реализован сервис на FastAPI. Он загружает сохраненную модель и предоставляет endpoints:

- `GET /health` — проверка состояния сервиса;
- `GET /model/info` — информация о модели и метриках;
- `POST /predict` — получение одного прогноза;
- `POST /predict/batch` — пакетное прогнозирование;
- `GET /predictions/logs` — просмотр логов предсказаний.

Пример входных данных для API:

```json
{
  "Подразделение": "Институт информационных технологий и компьютерных наук",
  "Курс_по_порядку": 4,
  "history_mean": 4.2,
  "last_mark": 4.5,
  "EGE_Информатика_и_ИКТ": 80,
  "EGE_Математика": 76,
  "EGE_Русский_язык": 85
}
```

Если часть признаков отсутствует, сервис заполняет их нулями, что позволяет выполнять прогноз даже при неполном наборе данных.

## 3.7 Логирование и мониторинг

Для приближения системы к production-подходу добавлены:

- логирование обучения модели;
- логирование метрик качества;
- логирование API-запросов;
- отдельный файл `logs/predictions.log` для предсказаний;
- заготовка для мониторинга дрейфа данных и деградации качества модели.

Это позволяет анализировать работу модели после внедрения: сколько запросов было выполнено, какие данные поступали на вход, какие прогнозы формировались моделью.

## 3.8 Итог доработки

В результате исходный исследовательский notebook был преобразован в MLOps-проект. Основная математическая и признаковая логика модели сохранена, но дополнена инженерными компонентами, необходимыми для промышленного использования:

- модульная структура проекта;
- воспроизводимый training pipeline;
- сохранение и версионирование модели;
- API для инференса;
- логирование;
- базовый мониторинг;
- документация и requirements-файл.

Таким образом, доработка заключалась не в замене исходной модели, а в переводе существующего решения из формата исследовательского эксперимента в формат прикладной ML-системы.
